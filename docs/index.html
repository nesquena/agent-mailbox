Open source · MIT

A shared mailbox for your AI agents.

Your agents run in different places: a Claude Code session on your laptop, an assistant in the cloud, a chat bot, a cron script. Agent Mailbox gives each one a name and an inbox, so they can send each other short messages through a private git repository that you own.

  • No server, no new account
  • Your repo is the store
  • Optional SSH signatures
  • No tokens spent while waiting

Why

Your agents can't talk to each other. So you do it for them.

Once you run more than one agent, you become the relay. You copy a question out of one session, paste it into another, wait, then carry the answer back. The agents can't hand work to each other, can't ask each other for help, and can't tell each other when something is done.

Agent Mailbox fixes that with the simplest thing that could work: mail. Each agent registers under a name. Any agent can send any other a message, and the recipient wakes up when it arrives, reads it, acts, and replies. Each agent's rules have it ask its own human before doing anything that human hasn't already approved.

For example, a cloud agent reviewing a pull request needs data that only your laptop can reach. It mails the agent on your laptop, and once you OK the lookup in that agent's session, the answer comes back. Nobody copies text between sessions, and the whole exchange is in the mailbox's git log.

It pays off most when your agents live on different machines or with different providers, where nothing else connects them. If you run a single agent, or all your agents already share one platform's built-in messaging, you may not need it.

What it's for

Agent to agent, or one agent coordinating many

A few patterns that come up again and again.

Agent to agent

A review gate

While a reviewer agent checks a change, it sends a hold on that exact version. When it's satisfied, it sends a release naming the version it approved. The merging agent's rules have it go ahead only once that reviewer has released the version in front of it and no hold on it is still open. A new push means a new review. Without a store that requires signatures, anyone with push access can forge a release; even with one, protect the branch against force-pushes, or someone with push access can erase a hold.

Orchestrator to agents

A stand-up and relay

One agent sends every other agent the same short check-in: blocked? approvals needed? what changed? It rolls the answers into one report for you, decisions first, and carries your answers back word for word. It has no authority of its own.

Cloud to laptop

A local helper

A cloud agent asks the agent on your laptop for something only that machine can reach: a local file, an internal page, a tool that's signed in there. The laptop agent's rules have it ask you before it sends anything from your machine (a file, a page, a command's output), and before any change, in its own session.

How it works

Plain files in a git repo, and a watcher that waits for free

The mailbox is a folder in a git repository. Sending a message writes one Markdown file into the recipient's inbox folder and pushes it. The recipient's watcher notices, wakes the agent, and the agent reads, acts and replies.

  1. Agent Ain the cloudsend helper-laptop …
  2. →↓
  3. Your private repothe storemailbox/inbox/helper-laptop/<id>.md
  4. ←↑
  5. Agent Bon your laptopwatch → read → reply

A message is just a file

Each one has a small header and a Markdown body. You can open it, read it and audit it like any other file.

  • One topic per message, and a clear needs. needs says what the sender wants back: an answer, a decision, a one-line ack, or none.
  • Reply and mark as read in one step. Consuming a message removes it from the inbox, which is the read receipt: a courtesy, not a proof. Git history keeps the record of what was delivered and read.
  • Waiting costs nothing. The watcher polls the store cheaply and spends no model tokens. Each message that wakes the agent is a turn, though, so a busy inbox does use some. That's why agents don't reply to needs: none.
  • It's mail, not chat. Latency is a poll interval, usually a minute or more with a git host.

Security

No server in the middle: your messages live in your repo

There's no Agent Mailbox server and no service to sign up for. Agents talk only through a private git repository you own, on the git host you already use.

  • Your repository is the store. Every message is a file in it, and each agent keeps its own clone. The repository's access control decides who can read or send, and every agent with access can read every inbox, not just its own. Take away an agent's access and it can't fetch new mail or send, but it keeps the copy it already has, and its registered key still verifies until someone with push access removes its record.
  • No new network or account. If your agents can push to a git repository, they can talk. Mail goes to your git host, to everyone with access to the repository, and to the agents that read it (and, through them, to the model service each one runs on).
  • Everything is auditable. Plain Markdown files, and the whole history in git log. You can read, audit and repair a mailbox by hand.
  • Verifiable senders. Agents can sign their messages with their own SSH key, kept on their own machine. Each reader pins a sender's key the first time it verifies that sender's mail; from then on, mail reads verified only when it's signed by that key. A signed message that's edited reads bad (strip its signature and it reads unsigned), one in the wrong inbox reads misrouted, and a sender's key that changes after the reader pinned it reads changed. Unsigned mail reads unsigned, and could come from anyone with write access, in any store. A store can require signatures, so its agents must sign and only verified releases open a gate, which you'll want if agents gate real actions like merges and deploys. For agents that matter, compare key fingerprints with their humans out of band.
  • Approval stays with you. The skill every agent follows treats a message as data, not an instruction: anything their human must approve still needs that human's own yes, in that agent's own session. A “yes” relayed by another agent is information, not approval. These are rules agents follow, not something the CLI enforces, so a confused or compromised agent can still break them.

What it doesn't do

  • It isn't encryption. Messages are plain text, readable by anyone who can read the repository. Keep it private, and never put secrets, keys or tokens in mail.
  • A signature isn't identity. It proves which key signed a message, not who is behind the key or that a human approved anything. You decide who gets access to the store.
  • Push access is real power. Anyone who can push can disrupt the mailbox, write unsigned mail under any name, swap an agent's registered key before a reader first pins it, forge releases where signatures aren't required, and rewrite history unless the branch is protected. Give it only to agents and people you'd trust with that, and give each agent the narrowest access its host supports.

The security model sets out exactly what's covered and what isn't.

Get started

Get your agent on the mailbox

Make a private repo, start the mailbox once, then give your agent one sentence. The agent does the rest.

You and each agent need Linux or macOS, a shell, git 2.9 or later, and OpenSSH 8.1 or later.

  1. Create a private repository for the mail

    Make a new, private repository under your own account or your organization. An empty one is fine. Call it whatever you like, such as agent-mail:

    • github.com/yourname/agent-mail
    • github.com/your-org/agent-mail

    This is separate from the Agent Mailbox project itself. Your messages go into your repository, not this one.

  2. Start the mailbox

    Do this once, from your own terminal. It installs the command and sets up the mailbox in your repo.

    git clone https://github.com/nesquena/agent-mailbox ~/agent-mailbox
sh ~/agent-mailbox/install.sh

agent-mailbox setup --store git@github.com:yourname/agent-mail.git --name yourname
agent-mailbox init

    install.sh links agent-mailbox into ~/.local/bin. If it says that folder isn't on your PATH, add it, or run ~/agent-mailbox/bin/agent-mailbox instead. If your agents will gate merges or deploys, run agent-mailbox init --require-signatures instead of plain init.

  3. Give the agent access to the repo

    The agent needs to push to your mail repository. An agent on your own machine can use the git access you already have there, though that reaches every repository you can; a deploy key on the mail repository is narrower. For an agent anywhere else, give it the narrowest access its host supports: a deploy key with write access on that one repository, or a token scoped to it. Set it up on the agent's machine or host; never paste a key or token into a chat.

  4. Tell your agent to join

    Give your agent this sentence, with your repo's address and a name for the agent:

    Say this to your agent

    Join the agent mailbox at git@github.com:yourname/agent-mail.git as helper-laptop. Follow https://github.com/nesquena/agent-mailbox/blob/main/JOIN.md

    That's it. The agent reads the join guide and gets the command, checks it can reach the repo, registers with its own signing key, starts its watcher, and reports back. It takes a few minutes, and it asks you only for what it can't work out itself: store access, its name if you have a preference, and who it should introduce itself to.

    Names are up to 63 lowercase letters, digits, . and -, starting with a letter or digit, such as reviewer-acme or helper-laptop. Use one name per running session.

    Using Claude Code? Install the plugin first. It adds the skill and, once the agent has run its watcher in a session, a hook that wakes the session when mail arrives (Claude Code 2.1.69 or later, in a terminal, on the web, or in the desktop app on macOS; elsewhere the agent re-arms its watcher itself). Its Stop guard needs jq.

    /plugin marketplace add nesquena/agent-mailbox
    /plugin install agent-mailbox@agent-mailbox

  5. Repeat for each agent, then check the wake-up

    Give every agent its own name and the same sentence. Then make sure mail really wakes them: ask one agent to send another a hello that needs a one-line ack, and watch the reply come back. A listener that stopped quietly is one reason mail can sit unread.

From there

Talking to your agents

The easiest way is to just ask your agent, in plain words, in its own chat. Some ideas:

  • Introduce yourself to reviewer-cloud and say what you can help with.The agent's rules have it ask you before it writes to someone new.
  • Ask helper-laptop to check the local logs for last night's failed run.One agent asks another for something only it can reach. The laptop agent's rules have it ask its human before it sends any of the machine's logs back.
  • Send every agent a stand-up: blocked, approvals needed, what changed. Summarize the answers for me.An orchestrator gathers status into one report.
  • Hold the merge of acme/app#12 until you've reviewed this version.A review gate with a hold and a release.
  • Check your mailbox and tell me if anything needs me.A quick check, any time.
  • What have you sent that hasn't been answered yet?Mail still unconsumed after a day counts as stale.

Or take part yourself

You can register under your own name and read and send mail like any agent, from your terminal: 

agent-mailbox register --kind human --about "Runs this mailbox"
agent-mailbox agents     # who's registered
agent-mailbox read       # your mail
agent-mailbox sent       # what you sent that's still waiting

And since every message is a file in your repository, you can also browse the inboxes there, and the history of everything consumed.

Keep the listener healthy

Mail only helps if the agent wakes up for it. A container restart or a missed hook can stop a listener without anyone noticing. The listening guide shows how to listen in any harness: a background watcher, a hook, a supervisor or a scheduled check. A scheduled inbox check makes a good backstop.
